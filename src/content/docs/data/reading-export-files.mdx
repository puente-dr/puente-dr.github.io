An export is one CSV file per form. This page is for whoever opens those files: the coordinator making a report, or the analyst who receives them months later. Most of the file is exactly what the surveyors typed. A few things are shaped differently from the app, and each one confuses someone who is not expecting it.

If you have not downloaded a file yet, start with [Exporting data](/docs/data/exporting-data/).

## One row per record, not per person

The `SurveyData` file — Resident ID in Collect — has one row per person. Every other file has one row per form filled in.

{/* claim: data-row-per-record */}
If you take vitals from the same person three times, the `Vitals` file has three rows for them. Each row already carries that person's details — name, community, organization — copied in from their Resident ID, so you can filter or pivot on them without joining anything.

<Aside type="tip" title="Count people in the people file">
The number of rows in a Vitals file is the number of readings taken, not the number of people seen. To count people, count the rows of `SurveyData`, or the distinct values of `objectId` in another file.
</Aside>

## Join files on objectId

{/* claim: data-join-objectid */}
When you do need to combine two files, join on the `objectId` column. It means the same thing in every file: **which person this row is about**. In the Vitals, Environmental Health, Medical Evaluation and custom-form files, the id of the form itself is in a separate column, `idSupplementary`, so the two never get mixed up.

Never join on a name or a community. Names are spelled several ways, and community names lose their accents in some files (see below).

## Records without a person

{/* claim: data-orphans */}
A form whose person record is missing still exports. It arrives with the person columns blank instead of being left out, so collected work never silently disappears from a download. If you see rows like this, tell your coordinator; they need repairing in Puente, not in the spreadsheet.

## Identical people collapse into one row

{/* claim: data-dedupe */}
The `SurveyData` export removes rows that are identical to each other. If two Resident IDs agree on the details it compares — name, nickname, sex, date of birth, phone, education, occupation, community, city, province, cédula, surveyor, organization, coordinates, photo and age, among others — they leave as **one** row. Insurance details are not compared, so two records that differ only in insurance also leave as one row.

That hides exact duplicates, such as a form sent twice. It also means the row count of the people file is not always the number of records in Puente: the two duplicates are still two separate people in the app, each with their own history. People who differ in any compared detail stay as two rows.

{/* claim: data-clean-duplicates */}
To fix duplicates at the source, use <UI>Clean</UI> in Manage, which shows how many duplicates it found. See [Data Curation](/docs/manage/data-curation/).

## Age is a subtraction

{/* claim: data-age-subtraction */}
When no age was typed on the record, the `age` column in the people file is **this year minus the birth year**, nothing more. Anyone whose birthday falls later in the year reads one year too old. For counting a community into age bands this is usually fine. When a single year matters — a pediatric cut-off, an eligibility rule — calculate the age yourself from `dob`.

If the surveyor typed an age, that number is kept exactly as typed — even when there is a birth date — and it does not go up as the years pass. If a birth date cannot be read at all, `age` is left blank rather than guessed.

## Accents in custom-form files

{/* claim: data-accents-stripped */}
In the four Puente files, text keeps its accents: `Peña`, `Baní`. In an export of a **custom** form, accents are removed from both the answers and the column headings — `Peña` becomes `Pena`, and `¿` and `¡` disappear.

<Aside type="caution">
The same community can therefore be spelled two ways across two files. A lookup or pivot that matches on community name will quietly miss rows. Join on `objectId` instead.
</Aside>

## Your questions become columns

{/* claim: data-question-columns */}
In a custom-form export, each question becomes one column, headed by the question's label. Whatever you type as the question in the Form Creator is what an analyst reads at the top of the column, so write it to be read on its own.

If you rename a question after people have answered it, the old and new answers still land in one column, under the current label.

{/* claim: data-column-collision */}
If a question has the same name as a built-in column — `communityname`, say — your column is renamed `communityname_from_custom_form`. Both columns are in the file.

## What is not in the file

{/* claim: data-not-in-file */}
- **Photos and signatures.** The people file has a `pictureURL` column: a link, not the image. Custom-form files carry neither.
- **The phone's own ids.** Ids a phone creates while offline help Puente recognise a form sent twice. They mean nothing in a spreadsheet, so they are left out.
- **Other organizations' records.** An export covers your organization only.

## FAQ

**Why does the Vitals file repeat the same name?**
One row per reading. The person's details repeat on each one.

**Which column tells me who a row is about?**
`objectId`, in every file.

**Can I fix mistakes in the spreadsheet?**
You can, but Puente will not know. Fix records in Manage, then export again.
